# Домашнє завдання №7. Аналіз життєвого циклу контейнера

**Автор:** Македон

Обрано **Варіант A — Аналіз життєвого циклу контейнера**.

Мета роботи — показати на практиці, що **контейнер це не «легка віртуальна машина», а звичайний Linux-процес у контрольованому середовищі** (PID/Network/Mount namespaces + cgroups). Для демонстрації запускаємо простий застосунок — вбудований HTTP-сервер Python (`python -m http.server`) — і досліджуємо його як процес: хто є PID 1, як контейнер реагує на сигнали завершення та звідки беруться логи.

> Для всіх дослідів використано офіційний образ `python:3.12-slim`. Нижче наведено команди, їхній вивід і короткі пояснення своїми словами.

## 1. Запуск контейнера

Запускаємо HTTP-сервер у фоновому режимі та публікуємо порт `8080` на хост:

```bash
docker run -d --name web -p 8080:8080 python:3.12-slim \
    python -m http.server 8080
```

Вивід (образ спершу підтягується з Docker Hub, а останній рядок — повний 64-символьний ID створеного контейнера):
```

3.12-slim: Pulling from library/python
72c03230f136: Pull complete
6ec7f4e699d7: Pull complete
4b6b2afbcb1e: Pull complete
6dc8148c4b61: Pull complete

Status: Downloaded newer image for python:3.12-slim
aa12b5ab001508018e5b53054036a08f40e2d089dfeea26936dff76ba8dd1f65
```

Пояснення параметрів:
- `-d` — *detached*, контейнер працює у фоні;
- `--name web` — людиночитна назва замість випадкової;
- `-p 8080:8080` — *port mapping* `host_port:container_port`: трафік з порту хоста `8080` прокидується у порт `8080` усередині контейнера (без цього сервіс був би недоступний ззовні, бо контейнер має власний network namespace);
- `python:3.12-slim` — образ;
- `python -m http.server 8080` — **команда, яка стане головним процесом контейнера (PID 1)**.

Перевіряємо, що контейнер працює:

```bash

```


## 2. Процес: хто є PID 1 усередині контейнера

Подивимося на процеси контейнера **з боку хоста** командою `docker top` (вона виконує `ps` на хості, тому не залежить від вмісту образу):

```bash
docker top web
```

Вивід:
```
UID                 PID                 PPID                C                   STIME               TTY                 TIME                CMD
root                2164566             2164543             0                   15:50               ?                   00:00:00            python -m http.server 8080
```

З боку хоста це звичайний процес із «великим» PID **2164566**. Але всередині свого PID namespace той самий процес бачить себе як **PID 1**. У мінімальному образі `slim` немає утиліти `ps` (пакет `procps` не входить до образу), тому пряма спроба завершується помилкою — і це саме по собі підтверджує тезу «контейнер = процес, а не повноцінна ОС»:

```bash
docker exec web ps -ef
```

Вивід:
```
OCI runtime exec failed: exec failed: unable to start container process: exec: "ps": executable file not found in $PATH
```

Використаємо те, що ядро надає завжди — віртуальну файлову систему `/proc` (PID 1 — це `/proc/1`):

```bash
docker exec web cat /proc/1/comm
```

Вивід:
```
python
```

```bash
docker exec web sh -c "tr '\0' ' ' < /proc/1/cmdline; echo"
```

Вивід:
```
python -m http.server 8080 
```

**Чому саме цей процес є PID 1.** Коли Docker запускає контейнер, він створює **новий PID namespace** і запускає передану команду як **перший процес** у цьому просторі імен — а перший процес завжди отримує номер 1. Тут немає `systemd`/`init`, як у звичайній системі: наш застосунок сам став PID 1.

**Практичний наслідок.** PID 1 у Linux — особлива роль:
- ядро **не застосовує до PID 1 дій за замовчуванням** для сигналів, які процес явно не обробляє (це захищає `init` від випадкового вбивства). Тобто PID 1 **ігнорує `SIGTERM`**, якщо для нього не встановлено обробник;
- PID 1 відповідає за *reaping* (прибирання) zombie-процесів; якщо застосунок цього не робить, зомбі накопичуватимуться.

Саме тому в продакшені часто додають мінімальний init (`tini`, прапорець `docker run --init`) або запускають застосунок напряму.

## 3. Завершення контейнера: сигнали та graceful shutdown

Команда `docker stop` зупиняє контейнер у два кроки:

```
docker stop → SIGTERM → чекає (default 10s) → SIGKILL
```

1. надсилає PID 1 сигнал **`SIGTERM`** (запит на коректне завершення);
2. чекає grace-період (за замовчуванням **10 секунд**);
3. якщо процес ще живий — надсилає **`SIGKILL`** (його неможливо ні перехопити, ні проігнорувати).

Перевіримо на нашому `web`. HTTP-сервер Python **не встановлює обробник `SIGTERM`**, а оскільки він ще й PID 1 — сигнал буде проігноровано, і Docker дочекається таймауту:

```bash
time docker stop web
```

Вивід:
```
web

real    0m10.693s
user    0m0.000s
sys     0m0.020s
```

Близько **10 секунд** — це і є grace-період: `SIGTERM` зігноровано → спрацював `SIGKILL`. Перевіримо код виходу:

```bash
docker ps -a --filter name=web --format "table {{.Names}}\t{{.Status}}"
```

Вивід:
```
NAMES     STATUS
web       Exited (137) 13 seconds ago
```

Код **137 = 128 + 9** означає завершення сигналом номер 9 (`SIGKILL`). Тобто контейнер було не зупинено коректно, а **примусово вбито**.

**Що відбувається, якщо процес ігнорує сигнал** (як вище): коректного завершення не відбувається — не закриваються з'єднання, не зберігаються дані, не завершуються воркери; Docker змушений убити процес через `SIGKILL`. Для веб-сервера це означає обрив активних запитів.

**Як зробити правильно (graceful shutdown).** Запустимо застосунок, який явно обробляє `SIGTERM`:

```bash
docker run -d --name graceful python:3.12-slim python -c "
import signal, sys, time
def shutdown(signum, frame):
    print('received SIGTERM, shutting down gracefully', flush=True)
    sys.exit(0)
signal.signal(signal.SIGTERM, shutdown)
print('app started as PID 1, handling SIGTERM', flush=True)
time.sleep(100000)
"
```

```bash
time docker stop graceful
```

Вивід:
```
graceful

real    0m0.535s
user    0m0.015s
sys     0m0.007s
```

Тепер контейнер зупинився **майже миттєво** (~0.5 с), бо процес сам коректно завершився по `SIGTERM`, не чекаючи `SIGKILL`. Код виходу — нульовий:

```bash
docker ps -a --filter name=graceful --format "table {{.Names}}\t{{.Status}}"
```

Вивід:
```
NAMES      STATUS
graceful   Exited (0) 14 seconds ago
```

**Окремий підводний камінь — `sh -c` як обгортка.** Якщо в Dockerfile написати `CMD ["sh","-c","python app.py"]`, то PID 1 стане `sh`, а `python` — його дочірнім процесом. `SIGTERM` від `docker stop` піде в `sh`, який **не передає сигнал дитині**, тож `python` його не отримає. Рішення — запускати процес напряму (`ENTRYPOINT ["python","app.py"]`, exec-форма) або додати init (`docker run --init`).

## 4. Логи: звідки вони беруться

Подивимося логи нашого сервера (команда працює і для зупиненого контейнера):

```bash
docker logs web
```

Вивід:
```
Serving HTTP on 0.0.0.0 port 8080 (http://0.0.0.0:8080/) ...
172.17.0.1 - - [19/Jun/2026 13:52:40] "GET / HTTP/1.1" 200 -
```

**Звідки беруться ці рядки.** Docker **не читає лог-файли з файлової системи контейнера**. Він під'єднується до файлових дескрипторів процесу PID 1:
- `fd 1` → `stdout`
- `fd 2` → `stderr`

усе, що процес туди пише, Docker перехоплює і передає у **logging driver**. Перевіримо драйвер:

```bash
docker inspect --format '{{.HostConfig.LogConfig.Type}}' web
```

Вивід:
```
json-file
```

Драйвер `json-file` (за замовчуванням) фізично зберігає логи у JSON-файлі на хості:

```bash
docker inspect --format '{{.LogPath}}' web
```

Вивід:
```
/var/lib/docker/containers/aa12b5ab001508018e5b53054036a08f40e2d089dfeea26936dff76ba8dd1f65/aa12b5ab001508018e5b53054036a08f40e2d089dfeea26936dff76ba8dd1f65-json.log
```

**Контрприклад — застосунок пише у файл, і `docker logs` порожній.** Якщо вивід іде не в stdout/stderr, а у внутрішній файл, Docker його не побачить:

```bash
docker run -d --name filelog python:3.12-slim \
    sh -c "echo 'hello to file' >> /tmp/app.log; sleep 300"
docker logs filelog
```

Вивід:
```
(порожньо)
```

А сам файл усередині контейнера існує:

```bash
docker exec filelog cat /tmp/app.log
```

Вивід:
```
hello to file
```

Висновок: у контейнерах файлову систему вважають тимчасовою, тому правильна модель — **логувати у stdout/stderr**, а збиранням і ротацією займається платформа (Docker, Kubernetes, централізоване логування).

### Підсумок завдання

**Що визначає життя контейнера і чому він завершився.**
Контейнер живе рівно стільки, скільки живе його **головний процес — PID 1**. Контейнер — це не окрема ОС, а *життєвий цикл одного процесу* в ізольованому середовищі: щойно PID 1 завершується (сам або примусово через сигнал), контейнер переходить у стан `Exited`. У нашому досліді:
- контейнер `web` завершився **кодом 137** — його було вбито `SIGKILL`, бо HTTP-сервер як PID 1 проігнорував `SIGTERM`, і Docker дочекався 10-секундного таймауту;
- контейнер `graceful` завершився **кодом 0 за ~0.5 с**, бо явно обробив `SIGTERM` і коректно вийшов сам.

**Ключові спостереження та терміни:**
- **контейнер = процес + ізоляція**: команда, передана в `docker run`, стає PID 1 у новому PID namespace; повноцінного userland (`ps`, `init`) у мінімальному образі немає;
- **PID 1 особливий**: ігнорує `SIGTERM` без явного обробника і має прибирати zombie-процеси; звідси практики `--init`/`tini` та запуск застосунку напряму, а не через `sh -c`;
- **сигнали керують lifecycle**: `docker stop` = `SIGTERM` → 10 с → `SIGKILL`; коди виходу `0` (коректно), `137 = 128+9` (`SIGKILL`);
- **логи беруться зі stdout/stderr** процесу (`fd 1`/`fd 2`) і передаються в logging driver (`json-file` за замовчуванням), а не з файлів усередині контейнера.

Головний практичний висновок: контейнер не додає застосунку «нових можливостей» — він лише *обмежує, ізолює та контролює*. Тому стабільність сервісу залежить від того, чи написаний застосунок з урахуванням контейнерного середовища: обробляє сигнали завершення, слухає `0.0.0.0` і логує у stdout/stderr.
